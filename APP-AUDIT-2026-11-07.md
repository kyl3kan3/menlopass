# App audit — November 7, 2026

Follow-up: implementation and release scope are recorded in [the audit fix release notes](RELEASE-NOTES-2026-11-07.md). The findings below preserve the original audit evidence.

Reviewed GitHub `main` at `208784efc4c72800eed665d25563973d6ee9b8ba` after fetching origin and fast-forwarding the local main branch. The previous checkout was an older feature branch. This audit covers the current merged web app and native source, not an independently verified App Store/TestFlight binary. No application fixes are included.

The core journeys work in the existing regression suite, but targeted checks found incorrect dating of health entries, lost treatment history, an offline navigation failure, and gaps in reports and native flows.

## Findings, in suggested fix order

### 1. P1 — Today's check-in can save to a past date

**Reproduced in Chromium.** Open Check in → Add context → Add more detail, select yesterday, then choose Back to focused check-in. The heading and values describe today, but the shared `curDate` still points to yesterday. Adding a hot flash writes yesterday's entry while the visible count remains unchanged. Confirm today's log confirms yesterday. Opening Care afterward also makes Today's care medication logging write to yesterday.

`app-views.js:2254` reads `entry(todayISO())`; the return handler at `2452` does not reset the date; confirmation at `2456` and other write handlers use `curDate`. The displayed and edited dates must agree, including Care actions.

A related navigation defect occurs even without changing dates: More detail sets `returnTab='checkin'` at `2453`, so the focused check-in's Today back button routes to itself at `2450`.

Local evidence: `test-results/flow-date-audit.cjs`, `flow-date-audit.log`, and `flow-date-mismatch.png`. The log records today's date as November 7, the write date as November 6, and the confirmed/adherence records on November 6.

### 2. P2 — A public page can replace the offline app

**Independently reproduced twice in Chromium.** Load the tracker, wait for service-worker control, open `/privacy.html`, go offline, and reopen `/` or `/index.html`. The Privacy Policy appears instead of the tracker; `#app` is absent. Other same-origin public pages can cause the same failure.

`sw.js:54–57` writes every successful navigation response under `./index.html`. Only tracker responses should update the tracker shell; public pages need their own cache entries and offline handling.

Local evidence: `test-results/flow-offline-audit.cjs`, `flow-offline-audit.log`, and `flow-offline-wrong-page.png`.

### 3. P2 — Restarting medication removes its previous stop history

**Reproduced in Chromium.** Stop a medication with a date and reason, then Restart it. The stop event and reason disappear from Journey and the report. A date during the pause changes from inactive to active when evaluated by `medicationActiveOn`.

`app-views.js:2582` clears `ended` and `stopReason` while retaining the original start date. A restart note does not preserve the prior treatment interval. Preserve stop/restart events and use those intervals when deciding whether a medication was active on a historical day.

Local evidence: `test-results/flow-restart-audit.cjs`, `flow-restart-audit.log`, and `flow-restarted-treatment.png`.

### 4. P2 — Trouble-sleeping ratings are omitted from appointment reports

**Observed in the UI and confirmed in source.** Choose Trouble sleeping in onboarding, record Moderate, confirm, and open the appointment report. The confirmed day is counted, but the rating is absent and Sleep says not tracked because that row only measures hours.

`app-views.js:1148` explicitly excludes `sleepq` from symptom averages; `1182` reads only `sleepH`. Report sleep difficulty separately from sleep duration. CSV export does retain the rating, and other expanded symptom keys participate in report averages.

### 5. P2 — Existing medication details cannot be edited

**Confirmed in the Care UI and source.** Users can add, stop, restart, archive, and record a treatment-change note, but cannot update an existing medication's name/dose, form, schedule, time, or notes. The Record change form at `app-views.js:2105` explicitly leaves those fields unchanged. A schedule or dose adjustment therefore leaves the current treatment details stale unless users create another medication. Add an edit flow that preserves historical values and treatment events.

### 6. P2 — Native deletion leaves app-owned export files behind

**Source-confirmed; not exercised on an iPhone.** `mobile/App.native.tsx:160–169` writes plaintext JSON/CSV exports into the app cache and retains them after sharing, including a cancelled share. PDF sharing at `189–205` also leaves an app-owned PDF. The deletion flow at `1248–1274` and `mobile/privacyFeatures.native.ts:228–247` does not clean these files.

Exporting and then deleting app profile/data can therefore leave health information in the app cache until OS eviction. Clean temporary exports after sharing and during deletion. Copies the user deliberately saved elsewhere remain a separate responsibility.

### 7. P2 if Android is supported — Journey and reports cannot unlock

**Verified from source and by evaluating the access-gate functions with Android's injected state.** RevenueCat initializes only on iOS (`mobile/App.native.tsx:884`), while Android receives `__MENO_NATIVE__=true` with inactive Pro state (`1489`). `app-views.js:2401–2414` gates Journey and reports on all native platforms. Android therefore shows a Pro requirement without a functioning purchase flow.

Android persistence also uses the plaintext fallback (`mobile/App.native.tsx:291–292`) and lacks the iOS security capabilities. Treat Android as unfinished unless the product is explicitly iOS-only; this audit did not run an Android binary.

### 8. P2 — Unreadable native records have no recovery screen

**Source-confirmed failure handling; no current user record was found damaged.** A record read/decryption failure rejects the combined startup promise (`mobile/App.native.tsx:844–865`), preventing HTML initialization. The app remains on Could not open peri (`1372–1373`), with no retry, backup import, or controlled reset action.

Keep the unreadable record intact, but provide a recovery route outside the health WebView. Verify it with a controlled corrupted record and a valid portable backup on a test device.

### 9. P2 — Current GitHub CI is red on Expo dependency validation

The [CI run for the audited commit](https://github.com/kyl3kan3/menlopass/actions/runs/41089555374) passed Build and test and Verify Expo package, then failed Verify Expo release configuration. Expo Doctor passed 20 of 21 checks and reported 12 patch-version mismatches: `@expo/ui`, `expo`, `expo-asset`, `expo-crypto`, `expo-dev-client`, `expo-document-picker`, `expo-notifications`, `expo-observe`, `expo-sharing`, `expo-splash-screen`, `expo-updates`, and `expo-widgets`.

Align the dependency manifest and lockfile with the SDK's supported versions and rerun CI. This result establishes a failed release check, not that all twelve packages cause runtime failures. The Vercel status for the same commit is successful.

Local evidence: `test-results/audit-github-ci.log`. Versions in that log are from the October 30 run; resolve the current expected versions when fixing.

### 10. P3 — Documented build/test commands fail on this Windows setup

`package.json:7` runs `python3 build.py`. Here `python3` resolves to the Windows Store alias and exits 9009, although `python` is installed (3.12.10). As a result, `npm test` fails before any tests run. Building with `python build.py` succeeds. Use a portable launcher or document/configure the supported Windows interpreter command.
